# 0016. Test in two layers: fast checks and real containers

**Status:** Accepted · **Date:** 2026-08-06

## The problem

Almost everything here is shell scripts that need root, a container, firewall
privileges and network access to do their job. The natural conclusion is that
you can only test it by building a container and poking at it — a several-minute
cycle for every change.

That's slow enough that in practice you stop running the tests, which is how
security tooling ends up broken.

## What we decided

**Structure the code so that the parts worth testing don't need any of that.**

The shell is split in two:

```
src/agentified/files/
├── lib/          ← text in, text out. No root, no network, no side effects.
│   ├── common.sh      option validation
│   ├── allowlist.sh   hostnames  → filter patterns
│   ├── firewall.sh    settings   → an iptables ruleset (as text)
│   ├── proxy.sh       settings   → a proxy config file (as text)
│   └── state.sh       the symlink logic
└── bin/agentified   ← the only part that writes files, starts processes
                        and talks to the kernel
```

Every genuinely tricky decision — is this hostname pattern too permissive? are
the firewall rules in the right order? does learn mode load the filter? — lives
in `lib/` and is a pure text transformation. Which means it can be tested by
calling the function directly.

That gives two layers:

### Layer 1: unit tests (~5 seconds)

Sixty-odd tests, written with [bats](https://bats-core.readthedocs.io/), run inside a
small Debian container. No root, no network, no image build.

```bash
make check     # shellcheck + every unit test
```

They cover the things that are hard to see by eye and catastrophic to get wrong:

- `example.com` must not match `evil.example.com`
- `.example.com` must match `a.b.example.com` but not `example.com.evil.net`
- the metadata block must come before the proxy's allow rule
- learn mode must not load the filter file
- `evil.com|.*` and `0.0.0.0/0 -j ACCEPT` must be refused

> The unit-test runner is **Debian-based on purpose**. An Alpine/BusyBox
> container would be smaller, but its `sed`, `awk` and `sort` behave subtly
> differently from the GNU versions in a real dev container — so tests could
> pass locally and the code fail in production.

### Layer 2: integration scenarios (minutes)

Eight configurations, each building a real container and running assertions
inside it, using the official `devcontainer features test` harness:

| Scenario | What it pins down |
|---|---|
| `claude_defaults` | Claude installs and actually runs |
| `claude_and_pi` | both agents coexist; Pi's state links correctly |
| `boundary_only` | the network boundary with no agent at all |
| `learn_mode` | permissive proxy, firewall still on |
| `off_mode` | nothing enforced, proxy still usable |
| `dns_blocked_and_cidrs` | strict DNS, plus direct-access address ranges |
| `ubuntu_base` | a different base image, to catch package-name drift |
| `root_remote_user` | running as root, where a lot of assumptions break |

Plus `verify`, an assertion suite that ships **inside** the container so users
can run it on their own machines when something looks wrong — not just CI.

## Why this split earns its keep

Three real bugs were caught by the fast layer or by an assertion written to be
picky:

1. **Validation inside a pipeline silently did nothing** — a `return 1` ran in a
   separate process and was overwritten by `sort`'s exit status. Invalid hosts
   were dropped and the build passed. See
   [ADR-0006](0006-reject-bad-options-loudly.md).
2. **Proxy settings in `containerEnv` broke the build itself** — caught the
   first time an integration scenario ran. See
   [ADR-0009](0009-keep-proxy-settings-out-of-containerenv.md).
3. **The agent installed but couldn't start** — caught because `verify` runs
   `claude --version` instead of just checking the command exists. See
   [ADR-0013](0013-run-only-the-agents-own-install-script.md).

None of those would have been found by reading the code.

## What it costs

- **A layer of indirection.** You can't read `bin/agentified` and see the
  iptables commands; they're produced by a function elsewhere. The trade is that
  the test file states the guarantees explicitly.
- **The integration suite is genuinely slow.** CI runs one job per scenario in
  parallel, and the fast layer gates the slow one so a typo never costs eight
  container builds.

## How CI is arranged

```
check (lint + unit tests)  ──►  one job per scenario, in parallel
                                   + the autogenerated default test
```

If `check` fails, nothing else runs.
